# Stage 1D-C — Password reset and global session revocation

## Boundary and API

`POST /api/v1/auth/password/reset` accepts `{ "token": "<opaque-token>", "newPassword": "<new-password>" }` only with a `local` or `test` profile (never `production`) and both `app.password-recovery.enabled=true` and `app.email-outbox.enabled=true`. The gates are independent of registration and login. It requires the anonymous `SESSION` cookie and `X-CSRF-TOKEN` from `GET /api/v1/auth/csrf`. Success is empty, no-store `204` with a server-generated correlation ID; it never authenticates the caller. Invalid, expired, revoked, reused, or ineligible tokens share `400 PASSWORD_RESET_TOKEN_INVALID`. Malformed JSON is `400 MALFORMED_JSON`, a password-policy failure is `422 VALIDATION_ERROR`, CSRF failure is `403 CSRF_INVALID`, direct-IP excess is `429 PASSWORD_RECOVERY_RATE_LIMITED`, and unavailable Redis/storage is `503 PASSWORD_RECOVERY_TEMPORARILY_UNAVAILABLE`.

The reset attempt limiter uses the existing independent recovery HMAC key, stores no plaintext IP in Redis, and defaults to 20 requests per direct IP per hour (`PASSWORD_RECOVERY_RESET_IP_HOURLY`). It runs before token lookup and fails closed on Redis errors. Only a verified `ACTIVE` account can use a token. The new password follows registration's 15–128 Unicode-code-point policy after NFC normalization, without trimming or character-composition rules, and uses the same versioned PBKDF2 encoder. Neither plaintext passwords nor raw tokens are stored or logged.

## Atomic PostgreSQL work and notification

The reset command uses one transaction. It resolves the hash-only token, locks the user before the token row, validates and consumes the token, updates `users.password_hash`, increments `users.auth_version`, cancels pending reset-link mail, and enqueues an encrypted `PASSWORD_CHANGED` notice in the existing PostgreSQL outbox. The notice's purpose ID is the user UUID; its JSON payload is `{}` and contains no token, password, or hash. If the outbox is unavailable or enqueue fails, the transaction rolls back, leaving the old password/version and the token's usability intact. No SMTP call runs inside this transaction.

The existing worker's claim, lease, bounded retry, and terminal-payload-purge behavior applies to `PASSWORD_CHANGED`. The Mailpit template confirms that a password change occurred and advises a user who did not initiate it to contact support and secure their email. Identity's eligibility port checks that the referenced user still exists. A reset link already in flight cannot be recalled, but its consumed token cannot be reused. The notice may be delayed or eventually fail delivery under the existing bounded retry policy; the committed reset is not reversed by a later SMTP failure.

## Session revocation and Redis transition

At login, `AccountPrincipal` stores the PostgreSQL account UUID and `auth_version`. Its stable `getName()` is the UUID string, which Spring Session 4.1.1 uses for principal indexing. Every protected request rereads the account from PostgreSQL, preserves the verified/`ACTIVE` check, and rejects a missing legacy version or any mismatch, invalidating that session. No version is accepted from Angular. A successful reset increments the database version inside the password transaction, so every earlier login fails on its next protected request. A request that passed authorization before the reset commits may finish; a protected request that starts after commit cannot use the older principal. New logins with the new password capture the new version.

Spring Boot 4.1.1 and Spring Session 4.1.1 support `spring.session.data.redis.repository-type=indexed`. This stage enables it while retaining namespace `makemymarriage:session`, the 30-minute inactivity timeout, HttpOnly cookies, CSRF, session fixation protection, and current-session logout. After commit, the reset command asks the indexed repository to delete sessions under the account UUID whose captured version predates the reset; a concurrent fresh login with the new version is left alone. Redis cleanup is best effort and catches failures; PostgreSQL version comparison remains authoritative. Earlier sessions written by the default repository may not have a principal index, so cleanup cannot promise to find them. Their versionless principal is rejected on use. No Redis data or development database is reset for this transition.

## Verification and limitations

With Docker Desktop available, `backend/gradlew.bat spotlessApply spotlessCheck build --offline` passed all 116 tests in 33 suites with no failures, errors, or skips. PostgreSQL/Redis/Mailpit Testcontainers tests cover token outcomes, concurrent consumption, rollback after notification enqueue failure, password normalization and login, multiple browser sessions, versionless/stale principals, indexed cleanup, cleanup failure, expiration, CSRF, rate limiting, outbox persistence, local SMTP delivery, and notification retry. Flyway V5 upgrade and Hibernate validation remain part of the full suite, as does Spring Modulith boundary verification. The [OpenAPI contract](../api/openapi.yaml) parsed as OpenAPI 3.0.3 with nine paths and 86 valid internal references. Changed-document links, Docker Compose configuration, and `git diff --check` passed. Tests used isolated containers and did not reset the development PostgreSQL or Redis services.

The Angular forgot/reset pages, registration UI, public recovery rollout, trusted proxy policy, and production mail provider remain deferred. The local Mailpit link points to a frontend route that is not yet implemented; extract its fragment token and submit it to the backend API with an anonymous CSRF session to exercise this stage.
