# Stage 1D-D — Angular password recovery and integration

## Scope and routes

This stage completes the local/test browser path for the existing Stage 1D-B/C APIs. It adds standalone `/forgot-password` and `/reset-password` routes and a working **Forgot password?** link on `/login`. It adds no registration UI, wedding feature, backend dependency, SQL migration, or new HTTP endpoint. Public signup and production password recovery remain disabled. The existing Git history and the uncommitted Stage 1D-A/B/C work are preserved; this stage is not committed or pushed.

The connected Figma file was inspected across all seven pages: Brand & Direction, Foundations, Controls, Patterns, App Screens, Prototypes, and Explorations. Its local variables include primitive colors, semantic Light/Dark colors, spacing, radius, and typography. Controls include Button and Input variants; the app screens cover onboarding and dashboard layouts, but no password-recovery page is present. The new pages reuse the Angular login layout and existing semantic tokens instead of introducing another design system or copying a nonexistent Figma screen.

## API, CSRF, and validation

`PasswordRecoveryApiService` uses the existing `CsrfService` and same-origin HttpClient. Before each unsafe request it obtains `/api/v1/auth/csrf`, then sends the session cookie and returned `X-CSRF-TOKEN`. Forgot submits a trimmed, lowercase email to `POST /api/v1/auth/password/forgot`; an empty `202` displays the same confirmation for every valid account state. It clears the entered email after acceptance. Direct-IP `429`, CSRF `403`, unavailable service, and other errors have accessible but account-agnostic feedback. The UI does not convert an uncertain response into a claim that an email was sent.

Reset submits `{ token, newPassword }` only to `POST /api/v1/auth/password/reset`, and only after explicit user action. It expects `204` and never signs the user in. The browser checks 15–128 Unicode code points **after NFC normalization**, rejects control characters, and requires matching confirmation; the backend remains authoritative and may return `422 VALIDATION_ERROR`. An invalid/expired/revoked/used token returns `400 PASSWORD_RESET_TOKEN_INVALID` and becomes terminal in the UI. CSRF `403`, rate `429`, service failure, and uncertain network errors have distinct messages. There is no automatic retry of a reset POST. A lost response may follow a committed reset, so the error asks the user to check connectivity or request a fresh link.

## Link and session security

The Mailpit link carries the opaque token in `#token=`, not the HTTP request path or query. The reset component removes the fragment with `history.replaceState` on first load and on later same-route navigation; it also checks after Angular router navigation settles because the router can restore a hash after `hashchange`. The token stays in the component only and is cleared on confirmed success or definitive invalidity. Password fields are cleared then as well. The document sets `no-referrer`; no token or password is put in browser storage, analytics, or application logs. Browser test failures avoid asserting a token-bearing URL as a literal.

A successful backend reset increments `users.auth_version` and makes every earlier authenticated Redis session unusable. The frontend immediately clears its cached user after a confirmed `204`, including while an older `/users/me` request is still in flight. Existing Angular `/users/me` restoration, protected-route guard, and account-page focus check clear stale displayed identity on `401` and route to sign-in. A network failure leaves session status unconfirmed; the existing logout path still consults `/users/me` before reporting success. The UI adds no client-side authorization rule.

## Verification and local manual run

Frontend checks: `npm.cmd run build`, `npm.cmd test -- --watch=false`, `npm.cmd run lint`, `npm.cmd run format:check`, and `npm.cmd run test:e2e`. Unit tests cover validation, normalized email, CSRF ordering, generic acceptance, loading and error states, fragment stripping, password policy, confirmation, 204, token reuse, and link navigation. Controlled Chromium fixtures cover navigation, safe feedback, fragment handling, and mobile layout. These fixture tests mock the HTTP endpoints and are distinct from the real-service journey.

The opt-in `frontend/e2e/password-recovery-real.spec.ts` runs against Angular on `127.0.0.1:4200`, Spring Boot on `127.0.0.1:8080`, and an **isolated** Compose project with PostgreSQL, Redis, and Mailpit. Set `MMM_REAL_SERVICES=1`, `MMM_REAL_POSTGRES_CONTAINER`, `MMM_REAL_REDIS_CONTAINER`, `MMM_REAL_DB_NAME`, `MMM_REAL_DB_USER`, and `MMM_REAL_MAILPIT_URL` to that project's values, then run `npm.cmd run test:e2e -- --grep 'real browser recovery|real recovery rejects' --workers=1`. The test never mocks an endpoint. It creates a unique local user, verifies Mailpit email, signs in through Angular, requests recovery, opens the real Mailpit link in Chromium, checks fragment removal, resets the password, checks two old sessions, verifies old/new password behavior and changed-password notification, and rejects reuse. A separate negative path checks CSRF, forced expiry in **that isolated database only**, and the Redis direct-IP limit. Never point these variables at the development database or Redis instance.

Verification on 2026-10-16: the forced offline Gradle `spotlessCheck build` passed all **116 tests in 33 suites**, with zero failures, errors, or skips. The Angular production build, lint, format check, and **51 unit tests in 10 files** passed. The normal Playwright run passed **9 fixture journeys** and skipped 3 opt-in real-service journeys. In fresh isolated Compose projects, both Stage 1D-D real-service journeys passed: the complete registration-to-password-change browser path and the live CSRF/expiry/rate-limit path. Flyway V5, Hibernate schema validation, Spring Modulith, transactional outbox, SMTP, and security tests are included in the backend suite. The existing development database and Redis were neither reset nor used for these tests. OpenAPI 3.0.3 has nine paths and 86 resolved local references; changed-document links and `git diff --check` passed.

For a manual run, start the existing local PostgreSQL, Redis, Mailpit, backend, and Angular servers as described in their READMEs. Enable `PASSWORD_RECOVERY_ENABLED=true`, supply a separate private `PASSWORD_RECOVERY_RATE_LIMIT_KEY`, keep the encrypted outbox enabled, and enable its local worker. Register and verify a local account using the existing API, then sign in at `/login`. Select **Forgot password?**, enter its address, open the delivered Mailpit reset link, and choose a new password. Confirm the old session is rejected and sign in again with the new password. Do not paste the raw reset token into a terminal command or share it in logs.

## Limits and next stage

The recovery endpoints and local Mailpit sender remain gated to `local`/`test`; no production email provider or public rollout is configured. The current API types are manually mirrored from OpenAPI until an approved compatible generator is added. A same-origin local HTTP browser run does not prove production HTTPS/proxy behavior. Token expiry and rate limits are backend-enforced; frontend messages do not reveal account eligibility. Milestone 1E may address Angular registration and broader account-lifecycle acceptance work only after separate approval. No wedding feature is part of that stage.

## Final 1D-D regression investigation (2026-10-16)

The old 1C-D real-service assertion expected Redis `EXISTS` for the primary session key to become zero immediately after logout. That was valid for the earlier default repository, but false after 1D-C selected `RedisIndexedSessionRepository`. The retained key is `makemymarriage:session:sessions:<id>`, a **hash containing actual serialized session attributes**, including `SPRING_SECURITY_CONTEXT`, rather than metadata alone. Spring Session 4.1.1's `deleteById` clears the expiry shadow and principal index, sets `maxInactiveInterval` to zero, and leaves the hash for at most five minutes so destruction events can inspect it. Its `findById` excludes expired sessions. The backend integration test asserts `findById` is null, the logout response expires the cookie, and an old cookie returns `401`; the live browser test now additionally checks the zero interval, short TTL, shadow/index removal, browser cookie removal, and replay rejection. No production logout code changed. The serialized context remains temporarily in Redis's protected session store, subject to the repository's bounded cleanup window; this is not an authenticated session or a demonstrated bypass. See [ADR-007](../adr/ADR-007-redis-sessions.md) and the [Spring Session 4.1.1 source](https://github.com/spring-projects/spring-session/blob/4.1.1/spring-session-data-redis/src/main/java/org/springframework/session/data/redis/RedisIndexedSessionRepository.java).

The negative recovery test previously sent 21 reset attempts from the same `127.0.0.1` source as the other browser journeys, filling their shared one-hour Redis IP limiter on reruns. It now allocates a distinct test-owned `127/8` loopback source address from a monotonic counter in the isolated Redis container and obtains its own CSRF session from that address. The first 20 attempts must return `400` and the 21st must return `429`, so the limiter stays enabled and its threshold is tested. Unique test identities isolate account-specific state. The allocator uses one test-only Redis key and does not flush any keys; no development Redis is used and no production limiter code changed. A run still requires the documented isolated PostgreSQL, Redis, and Mailpit services; repeated runs against that same stack passed without cleanup.

Final checks on 2026-10-16: forced offline `spotlessCheck build --rerun-tasks` passed the complete backend Testcontainers suite (116 tests in 33 suites), including Flyway V5, Hibernate validation, Modulith, password-reset integration, login/logout, session revocation, and Redis limiter checks. Angular production build, 51 unit tests in 10 files, lint, and Prettier check passed. All **12 Playwright journeys** passed together against the isolated services (9 fixtures and 3 real-service journeys) **twice in succession against the same PostgreSQL, Redis, and Mailpit stack** with the final monotonic-address allocator. The remaining limits are the local/test feature gates and lack of production HTTPS/proxy validation; Milestone 1E remains outside this stage.
